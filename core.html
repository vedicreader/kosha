core

Index your repository and its installed packages, then search them by meaning or by keyword.

This module builds the index that shows whether your code or one of your dependencies already has a helper you need. It splits source files into chunks, one per function, class or method. It stores each chunk with its metadata and an embedding. An embedding is a vector of numbers computed from the code, and chunks with similar meaning have similar vectors. A search combines two methods. Keyword search (SQLite’s FTS5) finds chunks that contain the words of the query. Vector search finds chunks whose embedding is close to the query’s embedding. No language model is involved, and everything runs locally.

There are two indexes. The repo index covers your own code and lives in .kosha/code.db inside the repository. The package index covers installed packages and lives in your user data directory (~/.local/share/kosha/env.db on most systems). Every project on the machine shares it, and a package version is indexed once. The Kosha class owns both indexes. The graph module holds the call graph built from them.

Utilities

These helpers support the indexing code below. Most users never call them directly.

parse reads Python source, from a string or a file path, and returns its syntax tree along with what kosha needs from it: a map from each imported name to its top-level package, the names of top-level functions and classes, the same plus module-level names assigned from a call, and a map from each imported name to its full dotted path. Results are cached, so calling it again on the same input is free. Source that does not parse gives None and empty collections.

Kosha

Kosha is the object you work with. Create one in your repository with Kosha(). It finds the repository root, opens the repo index in .kosha/code.db and the shared package index in the user data directory, and loads the embedding model. Its arguments let you point it somewhere else: dir sets the repository root, xdg_dir the data directory that holds the package index, and efn the embedding model, by default litesearch’s static code embedder. install_skill=True also installs SKILL.md. Set busy_timeout (in milliseconds) when several processes or threads write to the index at once, as update_pkgs(parallel=True) does.

Inside, the object holds three stores: code_st for repo chunks, env_st for package chunks, and pkg_st for package descriptions. Four plain tables sit beside them. packages records each indexed package version, and pkg_deps and repo_deps count which packages each package or repo module imports. repo_file_imports keeps the packages each repo file imports, so an incremental update_repo recounts repo_deps without parsing unchanged files.

Indexing packages

update_pkg indexes one installed package. It parses the package’s source files into chunks, stores them in the package index with an embedding, and records in pkg_deps how many of its modules import each other package. A package already indexed at its installed version is not parsed again, unless you pass force=True, but any of its chunks still without an embedding are embedded. update_pkgs does the same for a list. Use parallel=True to index several packages in threads at once; that needs a Kosha built with a busy_timeout, and without one it raises an error, as the test below shows. rm_pkg removes a package, or one version of it, from the index.

process_env computes embeddings for package chunks that were stored without one, for example after update_pkgs(embed=False); reembed=True recomputes all of them. It works through embed_missing, which does the same for any store and keeps its HNSW index in step. nuke deletes the repo’s .kosha directory, which holds the repo index and the call graph, and with env=True also the shared data directory holding the package and docs indexes. count_imp counts, for a list of files, how many import each top-level package.

update_repo indexes your own code. It judges what is installed by the *.dist-info folders in each site-packages folder it knows. It lists folders and never imports a package. It knows these folders: the folders the indexed chunks were read from, the nearest .venv above an editable install’s source, and the current project’s environment. A folder that no longer exists holds nothing.

A package keeps its chunks while any of those folders holds it at any version. A package has one set of chunks in the index, from whichever version was synced last. A chunk’s version records the version at which the chunk was first stored. An unchanged function from an old release is still current code. A chunk’s version does not identify stale chunks. Each packages row, one per indexed version, stays while some folder holds that exact version. Removing a package also drops its description and import counts. prune_env then runs VACUUM once to shrink the file. Searching

A query can carry filters as key:value tokens next to the words, as in merge dicts package:fastcore path:basics. parseq splits a query into the plain text and a dict of filters. The keys are file, path, package, lang and type, and the short forms people tend to type first also work: pkg, dir, folder, ext, plurals such as packages, and so on. A value can list several options separated by commas. A trailing !, as in package!:fastcore, is accepted and means the same as without it, because every filter already excludes everything that does not match. A token that looks like a filter but has an unknown key, such as libr:litesearch, is reported under _unknown, so a caller can warn about it instead of silently searching for the literal text. If a query holds nothing but filters, the whole query is kept as the search text.

env_context searches the package index and repo_context searches the repo index. Each parses the filters, embeds the query, runs one search that combines keyword and vector matching, and returns hits with their content and metadata. Use one of them when you know which index you want. Kosha.context, defined in the graph module, searches both indexes, reranks the hits for code and adds call-graph details. Use Kosha.context by default.

Both take limit, an extra SQL where, and rerank=True to reorder the hits with a flashrank cross-encoder, a small model that scores each hit against the query. When reranking, kosha first retrieves a wider pool of candidates (fanout) for the reranker to choose from. It then cuts the result to limit. pkgs2consider returns the names of indexed packages, or with sys_wide=False only those indexed at the version your project uses.

One row shape

A tool that shows kosha hits next to hits from other sources, such as documentation or notes, needs every hit in one format. code_row turns one hit from repo_context or env_context into an AttrDict with six keys: source (which index the hit came from), ref (the dotted name, or the path), title, where (path:line), text (the first 600 characters of the chunk) and open. open is a hint for how to open the hit, such as symbol('pkg.mod'). rows runs the searches and returns the hits in that format. It searches the repo index by default. Pass env=True to add the package index.

Docs index

Code chunks suit code, but a README or a docs/ folder reads better as whole sections. kosha keeps a third index for such prose, built on litesearch’s Index, which splits documents by their headings and can search, list and return whole sections. It lives in the shared data directory (docs.db), next to the package index, and is created the first time you use it.

add_docs adds a folder of documents, a single file, or a dict of {title: text}, and returns the number of chunks added. add_pkg_docs adds a package’s full README. docs_context searches the docs index. By default it returns ranked sections, each with a node_id you can pass to k.docs.read to get the whole section; sections=False returns the raw chunks. The docs index uses the same embedding model as the code indexes, so only one model is loaded.

Keeping syncs fast
