graph

A call graph of your code and its packages, for seeing what a change will touch.

Edges come from two passes over the source. The static pass uses ast-grep to find every place a function, class or method is named inside another and binds that name to its definition. The dynamic pass uses Python’s ast module to find dependencies that are not written as calls, such as decorators and handler tables.

CodeGraph holds the graph in one SQLite database. Pass a file path, or ':memory:' for a throwaway graph. Its main tables are graph_edges (caller, callee, kind, confidence) and graph_nodes (node, flavor, file, method name, PageRank, in and out degree). co_dispatch stores groups of peer functions, file_index stores a hash of every analysed file so that later syncs can skip unchanged files, and pending_attr_calls holds method calls that can only be resolved once the whole graph is known.

You rarely build a CodeGraph yourself, because Kosha.graph opens the one for your repository. The examples below use an empty in-memory graph.

Dynamic edges

Much of the structure of a Python program is never written as a call. A web framework calls hello because @app.route('/hello') registered it, and fastcore’s @patch turns a plain function into a method of a class. dyn_edges reads one module’s source and returns these dependencies as edges, with these kinds:

  • decorator: @app.route(...) above def hello gives an edge from app to hello. Confidence is 0.95 when app comes from a known web framework (fasthtml, flask, fastapi, starlette, django and a few others), 0.75 when the decorator’s method name sounds like registration (route, add, register, get, post, on, use and so on), and 0.5 otherwise.
  • registration: a call such as app.register(hello), where hello is defined in the module, gives an edge from app to hello, with the same confidence rule.
  • connect_body: a function named setup, register, connect, init_app, create_app or similar, whose body passes a function to a method of its first argument, gives an edge from the setup function to that function (0.9).
  • patch: @patch def f(self:Table) gives an edge from Table to f (0.9).
  • delegates: @delegates(target) on wrapper gives an edge from wrapper to target (0.85).
  • co_dispatch: a module-level list, tuple or dict of the module’s functions, such as HANDLERS = [a, b, c], makes those functions peers. When you add a new handler, its peers show the pattern to follow. Peers are stored as groups in the co_dispatch table, not as edges.

Static edges

static_edges reads source with ast-grep and returns two things: a list of edges of kind static with confidence 1.0, and a dict of node metadata keyed by node name (flavor function, class or method, the file, and the short method name). Pass either sources, a dict of {module name: source text}, or filenames with the root directory that module names are taken relative to.

An edge means the caller uses the callee by name. A call helper() counts, and so does passing helper as a value. To decide which definition a name refers to, kosha tries three places in order: a definition in an enclosing scope (the function, its class, the module), then the module’s imports, then the one definition in the whole corpus with that name, if there is exactly one. Two cases are left out on purpose. An attribute is followed only when it is reached through self, because x.get() could be the get of any object. A Python builtin such as list is never bound to a function elsewhere that happens to share its name. A name that only appears in an import statement makes no edge.

The first example graphs two lines of source. A file that does not parse gives no edges and no nodes.

Building a graph

Every node also gets three numbers. in_degree is the number of edges into it (its callers) and out_degree the number out of it (its callees). PageRank, the algorithm Google first used to rank web pages, gives a node a high score when many nodes depend on it, or when nodes that are themselves heavily used depend on it. kosha uses it as a measure of reach: changing a node with a high PageRank affects more code. Degrees are refreshed after every update. PageRank is slower to compute on a large graph, so it is recomputed only when the number of edges has changed by more than 10% since the last computation.

from_sources builds a graph from a dict of {module name: source text}. It is the quickest way to try the graph on a snippet, as the example under the PageRank tests shows. Besides functions and classes, it records module-level names bound to a lambda, partial, bind or curry as function nodes.

To graph real code, use from_dir for a directory of .py files or from_pkg for an installed package, which it finds through Python’s import system. Both pass their files to process_files, which you can also call with your own list. Extraction runs in worker processes, sz files at a time.

Module names come from file paths. from_dir names modules relative to the directory’s parent, so from_dir('../kosha') gives kosha.core, kosha.graph and so on. process_files without a root uses each file’s import root, the nearest ancestor directory without an __init__.py. from_dir and from_pkg also take globtastic filters such as skip_folder_re. Each method returns the graph, so calls chain.

Querying the graph

All queries take full node names. callers(n) and callees(n) return the nodes one edge away, and with_kind=True returns (name, kind) pairs instead. neighbors(n, depth) returns every node within depth edges in either direction.

co_dispatched(node) returns the other members of the node’s co-dispatch group: the functions it shares a route list or handler table with. ranked(k, module) returns the k nodes with the highest PageRank, optionally only those under a module prefix.

short_path(src, tgt) follows edges from caller to callee and returns the shortest chain from src to tgt, or an empty list when there is none. short_paths(nodes, k) does this for every pair among the first k nodes and returns the paths longest first. edge_kinds() counts the edges of each kind.

node_info(node) is the one to call before changing a function. It returns the node’s row from graph_nodes together with its callers, callees and co-dispatch peers. node_infos returns the same records for many nodes with one query per table, which is what Kosha.context uses to annotate search hits.

Ranking

A search returns candidates from two lists, the repo index and the package index, merged by reciprocal rank fusion (RRF): each candidate scores 1/(k + rank) for every list it appears in. That order knows nothing about code. rank_results adjusts the scores with rules adapted from the semble code-search library:

  1. If the query looks like a symbol (is_symbol_query: a dotted or :: name, a leading underscore, or a capital letter or underscore inside, as in Client, Sinatra::Base, _private), chunks that define it (def Client, class Client, CREATE TABLE Client) get a large boost, half again as large when the file name matches as well.
  2. Otherwise the query is treated as natural language. Chunks whose file or folder name matches words of the query get a boost in proportion to the share of words matched, and CamelCase names in the query give a smaller definition boost.
  3. Chunks from a package the query mentions are multiplied by 1.5.
  4. A file with several high-scoring chunks has its best chunk raised.
  5. Paths that are rarely the answer are penalised: tests, compat or legacy folders and examples are multiplied by 0.3, __init__.py files by 0.5, and TypeScript .d.ts files by 0.7.
  6. Each further chunk from a file already chosen counts for half as much as the one before, so a single file cannot fill the results.

Incremental sync

Re-reading a large environment takes minutes, so syncing reads only files whose content has changed. file_index stores a BLAKE2 hash of every analysed file. sync_dir compares hashes, drops the nodes of deleted files, and re-extracts changed ones. In the default mode='fast' a changed file’s own nodes and outgoing edges are replaced while edges from other files into it are kept, and edges into nodes that no longer exist are removed. mode='full' re-extracts through process_files, which uses worker processes. sync_pkgs does the same for each installed package’s directory, and CodeGraph.sync runs both, then refreshes PageRank if anything changed. Pass metrics=False to skip that and call recompute_metrics() once after several syncs. force=True re-reads every file.

Syncing and searching from Kosha

Kosha.sync is the one call that brings everything up to date. It re-indexes changed repo files (update_repo), indexes installed packages (update_pkgs) and updates the call graph, running the three in parallel threads unless in_parallel=False. With no pkgs, it indexes the packages that status() reports as stale. repo, env and graph switch each part off. embed=False stores new chunks without vectors, so only keyword search finds them until process_repo or process_env adds the vectors. It returns the three parts’ results, not the Kosha.

Kosha.context is the search to use by default. It runs repo_context and env_context in parallel, merges their hits with RRF, reorders them with rank_results, and keeps the top limit. With graph=True, the default, each hit also carries its graph record: pagerank, in_degree, out_degree, callers, callees and co_dispatched.

Two ways of naming a package behave differently. A package:fastcore filter skips the repo search and returns only fastcore’s code. A package name written as a plain word, as in fastcore merge dicts, only boosts that package’s chunks, and other packages still appear. compact=True returns slim dicts with mod_name, docstring, lineno, path and sig, the first line of the chunk. rerank=True reorders the final hits with a flashrank cross-encoder. That needs flashrank’s model on disk, and the saved output below shows it skipped on a machine without it.

Package dependencies

When kosha indexes a package it also counts which other packages its modules import, in the pkg_deps table (from_pkg, to_pkg, n_modules). dep_stack(seeds, depth) walks that table breadth first. The first layer is the seeds, the second the packages they import, and so on, depth layers down. With no_sys_pkg=True it keeps only names that are installed distributions (is_sys_pkg), and allow restricts the result to a list you give. Use it to see what sits under a package before reading its code.

top_nodes(pkg, k) returns the k public names of a package with the highest PageRank: its most used entry points. api_call_paths(from_pkg, to_pkg, k) takes the top k of each package and returns {target: path} for the shortest call paths from the first package’s entry points to the second’s. An empty dict, as in the fastlite example, means none of the top nodes reach each other.

Where to add code

where_to_add(description) suggests where new code should go. It runs context on the description and, for each hit in the repo index, returns node, path, insert_after, co_dispatched and pagerank. insert_after is the last line of the hit, or of its last co-dispatch peer in the same file, so new code lands after the group it belongs to. Hits from installed packages have no place in your repo and are skipped. Other keyword arguments go to context.
